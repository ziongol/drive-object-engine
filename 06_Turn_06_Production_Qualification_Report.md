## 4. Actual asymmetric receipt signing

### 4.1 Algorithm and native boundaries

The new algorithm identifier is `ECDSA-P256-SHA256-DER`. This is a public/private-key signature, **not HMAC and not an unkeyed checksum relabeled as a signature**. No elliptic-curve arithmetic is implemented in Python.

On macOS, standard-library `ctypes` calls Apple Security.framework and CoreFoundation for `SecKeyCreateRandomKey`, public-key extraction, key import/export, `SecKeyCreateSignature` and `SecKeyVerifySignature`. The selected message algorithm is `kSecKeyAlgorithmECDSASignatureMessageX962SHA256`. Apple documents the signature operations and its uncompressed EC external representations; API existence does not qualify this particular ABI adapter on the lab's Mac. [S01–S03]

On Linux, a separately identified system OpenSSL 3 EVP backend executes the same P-256/SHA-256 signature profile. It is used for this local test run and does not masquerade as Apple Security. Backend absence or incompatible key format fails closed. No command-line signer, pip installation or downloaded code is a runtime fallback. [S04–S06]

Private keys are generated on the configured host and remain in an unsynchronized private root, with 0700 directory and 0600 file policy, no-follow access, ownership checks and private/public consistency checks. These are file-backed software keys. This release does not claim Secure Enclave storage, Keychain access controls, nonexportability, resistance to a malicious same-user process, or secure erasure of every memory copy.

No live private key is included in the release archive. Tests generate disposable keys. The retained interoperability fixture contains only a public key, message and signature.

### 4.2 Exact-byte domains

An outer `gdoe-signed-receipt/1` envelope has exactly `protocol`, `algorithm`, `key_id`, `payload_b64` and `signature_b64`. The signature covers the exact canonical payload bytes preceded by `GDOE-SIGNED-RECEIPT-V1` and a NUL byte.

The payload binds the store and authority, task key K, submission R, request Q, decision A and retained generation/snapshot G. It includes original acceptance and verification bytes as canonical base64 with separate SHA-256 values, an audit-event checkpoint, build fingerprint, preparation time, qualification label, and an optional activation record. The public-key identity is a SHA-256 over a separate public-key domain and the 65-byte uncompressed public key.

Original receipts are not parsed and reserialized into substitutes. Their exact bytes are embedded. The verifier checks the signature, enrolled signer scope, canonical encoding, embedded digests, task/root/decision relationships, audit-event relationship and activation evidence where present. Successful verification does not mutate canonical task state.

ECDSA may produce different valid signatures for repeated signing of one payload. Therefore the first complete signed envelope is durably stored before publication and every retry reuses those **same envelope bytes**. The content-addressed filename identifies that persisted envelope, not an assumption of deterministic ECDSA output. `SIGNATURE_PROTOCOL.md` specifies the field and trust contract.

### 4.3 Public trust and revocation

A key offered in an untrusted Drive file does not enroll itself. The operator exports a verification-only trust snapshot from the local authority and supplies it through an already authenticated channel. Trust is scoped to one store and authority. The key ID, algorithm and allowed state must match; unknown/revoked keys fail.

Rotation makes the former key verification-only. Drain pending unsealed jobs before planned rotation: an old queued job does not silently change signers. Sealed envelopes remain replayable under the retained verification key. Revocation rejects even historical signatures under that key. An offline verifier using an older trust snapshot does not learn revocation automatically.

An optional minimum decision sequence rejects older observations below an enrolled checkpoint. It is not a discovery service for the globally newest state. A signature authenticates a scoped assertion under trusted key custody; it does not certify every Google replica or an operator's truthful interpretation of test evidence.

## 5. Durable outbox and exact historical evidence

### 5.1 State and transaction ordering

`drain_receipts(maximum=16, offline=False)` performs one bounded iteration. It requires an explicitly installed extension and enrolled signer. New historical outbox intents are derived from committed acceptance rows and original receipt bytes. The stable source identity prevents a second job from being invented for an exact replay.

The service persists the body first, then persists the signed envelope and its digest before provider I/O. It records a dispatch attempt and an uncertain outcome before the potential publication. A worker performs no-clobber installation and readback at:

`<enrolled intake>/receipt_outbox/<envelope_sha256>.json`

After a conclusive matching readback, the registry records `LOCAL_PUBLISHED`. A crash after final rename but before that update leaves the same bytes, target and job available for reconciliation. A differing occupied target is preserved and rejected; it is never overwritten or repaired in place.

A per-job private guard is inherited by the publisher so a late worker cannot lose its ownership merely because its parent stopped waiting. Provider I/O is outside the authority transaction and authority guard. The transaction does not extend across SQLite and Google Drive. [S08, S09]

Temporary staging inside the provider tree may synchronize partially. The guarantee is that partial/unverified content cannot be treated as a valid signed result—not that Drive is prevented from seeing every staging write. Local publication remains explicitly `remote_evidence: NOT_ASSERTED`.

### 5.2 Finite retry, offline and scheduling behavior

The outbox has persistent attempt accounting, a maximum batch of 128, a default batch of 16, and eight dispatches per job/window. Exhaustion returns `HOLD_RETRY`. Restart or reconnect does not reset that counter. Reopening a window is an explicit administrative action with a recorded reason.

The new receipt service does not implement the entire earlier elapsed-active-time/equal-jitter scheduler. Its bounded iteration is called by the existing trusted lab loop, which must enforce cadence and network-cost policy. It does not install a daemon or promise future activity after the caller exits. `--offline` initiates no new provider work or outbox mutation; it cannot stop the native Drive client's already queued traffic.

For NATIVE54, the old unsigned `service_receipt_outbox` remains in the byte-preserved original source. Switch the controller's receipt loop to the new `ReceiptService`; do not run both exporters and assume one configures the other. Legacy outbox rows are marked `SIGNED_ENVELOPE_LOCAL_PUBLISHED` only to describe the new envelope's publication, not to falsely claim publication of an old raw filename.

### 5.3 Audit checkpoints and their limit

CHAT66 appends a hash-bound audit seal alongside its applicable local audit transition. NATIVE54's unchanged core continues writing its original audit rows; the extension verifies the already sealed prefix and seals its newly observed tail at an extension checkpoint. It does **not** claim a later signature was created at the original acceptance time.

Additive triggers protect immutable receipt intent, write-once envelope bytes, audit history and retained seal rows. NATIVE54 also makes original acceptance rows update/delete-protected. The signed envelope binds the selected committed acceptance event and its task/root/decision relationships.

This is tamper-evident evidence under the stated local-key and historical-continuity assumptions. Restoring the entire database, keys and checkpoints to an old consistent image can roll back the trust base. Detecting every such rollback requires an independently retained head or different trusted mechanism; no such network lock service is silently introduced.

## 6. Qualified activation without rewriting history

Historical signing is available without inventing production qualification. NATIVE54's original `NOT_GRANTED` values remain inside its original receipts; the historical outer label is `LAB_CANDIDATE_UNQUALIFIED`. CHAT66 likewise preserves its original recorded qualification and byte identity.

`activate_receipt(receipt_sha256, qualification_id, operation_id)` is a separate operation. It checks an independently enrolled qualification record for the current runtime fingerprint, environment and scope, captures a fresh private verification of the accepted snapshot, checks retained generation protection and authority conditions, and commits a new activation attestation with its outbox intent. It does not create another K acceptance, allocate a replacement historical decision or edit the original acceptance time.

The enrollment gate requires the complete named AT-01–AT-32 qualification record and the new capabilities `native_signatures`, `receipt_drainage`, `generation_lifecycle` and `wrapper`. Scope is `PROCESS_CRASH_QUALIFIED`. A method count alone cannot satisfy those requirements. The administration path checks the record binding; it does not independently prove that a trusted operator's PASS declaration is true. Evidence review is a real external responsibility.

Positive activation tests in this package use an isolated `FIXTURE_ONLY` qualification mock. No production CLI option creates that fixture scope. Old-signature verification, newly qualified activation, current private byte health and remote replication are different observations.

## 7. Generation lifecycle and multi-producer decisions

### 7.1 Retirement and floor

`retire_generation(G, reason)` rechecks eligibility under the same registry serialization as pin changes. An eligible `AVAILABLE` generation becomes `RETIRING`; an already retiring/absent generation is an idempotent observation. Active reader, acceptance, preparation, unresolved source, export or other protection prevents retirement. Installed triggers reject new pins on retiring or absent generations.

Deletion happens after that transition and targets the exact generation-specific private path. A per-generation guard remains with the remover. After interruption, an already absent path can be reconciled. No reusable digest pathname stands in for G; a delayed cleaner cannot target a replacement just because its content hash is equal.

`protected_floor_gb` is an exact decimal string derived from protected accounted bytes. A caller's requested target does not authorize releasing pins. Prune may remove eligible garbage yet return `HOLD_RESOURCE` because the protected floor remains above the requested maximum. Dry-run makes no retirement/deletion transition. Logical accounted bytes are not a promised amount of physical APFS space recovered.

Unmanaged default exports stay retained until an explicit end-of-use release. Reader lifetime does not expire with a worker's lease, an idle period or command exit. Corrupt incident-held content is not discarded just because it is ineligible for reuse.

### 7.2 Arbitration

Both original local brokers retain their authority semantics. `arbitrate_candidates()` is a bounded adapter for independent producer submissions, not another consensus system. Every actual admission enters the selected profile's durable request order and unique task decision transaction. K remains `(store, campaign, task, task revision)` and excludes authority epoch. An already accepted different root loses; an exact existing decision is replayed with its original bytes. Uncertain authority outcome prevents unsafe advancement.

Determinism means the same recorded authority history replays the same winner. It does not promise the same winner under every network-arrival schedule or permit two host-local databases to act as simultaneous authorities. The local concurrency tests execute real subprocess competition and distinct producer candidates. They do not claim a live two-device Google Drive delivery experiment.

## 8. Wrapper and platform fault harness

The wrapper reads the explicit private configuration and routes to NATIVE54 or CHAT66. It preserves each profile's current Turn 5 root-hash `get` interface, performs strict option checking, and offers private-only `status`. It has explicit `commit` and `drain` verbs so none of the required short verbs hides canonical admission or transport work.

The bundled `lab` is a standalone sample launcher. This delivery does not overwrite the actual Gemini Operator Lab dispatcher or edit its repository. An existing Python dispatcher can route `drive` arguments to `tools.drive_engine.main`. The entire sibling module set must be installed together; copying only the wrapper is insufficient.

Both test profiles perform real owned filesystem reads before their mocked availability or error response. Cases include successful modeled hydration, injected EIO after a real read, signal termination after a real read, delayed completion, finite worker waiting and exact destination checking. The controller checks child status rather than forwarding the child signal into the host or interpreting partial output as success.

A separate child maps and then truncates its own private test file to exercise an actual OS backing-file fault. No core CloudStorage acquisition path uses mmap. Python's deferred signal handling does not reliably repair a native synchronous fault by returning to the faulting instruction, so containment—not such a recovery loop—is the intended mechanism. [S07]

Mocks are test-only entrypoints. No public config or CLI field lets an untrusted producer select them as a production worker. The wrapper and status path do not probe cloud files merely to manufacture progress information. Actual FileProvider flags, live hydration, Apple crypto ABI behavior, controlled cellular recovery and independent-device ingress remain separately qualified conditions.
